Applied Pattern: MVC Model (Model - View - Controller)

SE Ch3 Slides 17–19

Definition in Slide 17: "Separate display and interaction of system data. The system is structured into three logical components that interact with each other." The Student Attendance & Intelligence System (SAS Enterprise) implements this pattern without deviation:

Diagram: MVC Interaction Sequence (Exact replication of Slide 17)

Initiates actions: login, enter PIN code, submit excuse, override status

➔ (1) HTTP / UI Request

SQLite3: attendance.db (ACID Transactions)

database.py & attendance.db

Slide 17 Definition: "The Model component manages system data and the operations associated with that data."

  • Manages 8 relational tables (Users, Courses, Sessions, etc.)
  • Thread-safe DBConnection context manager
  • Executes CRUD queries with SQL injection prevention
  • Enforces foreign key cascades and check constraints
V View Component
index.html (Client UI)

Slide 17 Definition: "The View component defines and manages how data is presented (displayed) to the user."

  • Screen 0: Role-based Sign-in Gateway

Course Design Quality Metrics

Slides 11–13, 19

Evaluated against the core design measurements taught in Chapter 3:

High Cohesion (Good — Slide 11, 13, 19) Verified

"Cohesion: The degree of relevance of the components in the module." (Slide 11). Each module has single, focused responsibilities: `database.py` contains only table CRUD; `AttendanceLogic` contains only business rules; views contain only layout and event listeners.

Loose Coupling (Good — Slide 11, 12, 19) Data Coupling

"Coupling: The degree of interdependence between modules." (Slide 11). Modules interact through primitive data structures (JSON/dict parameters). The UI has zero knowledge of SQL or internal database table schemas.

Advantages Realized in SAS (Slide 19):
  • Concurrent development: UI screens and backend SQLite logic created in parallel.
  • Easy to maintain: Modifying the styling or screens requires zero changes to database queries.

Database Design Levels & Methodology

SE Ch3 Slides 29–30

The database design follows the rigorous 3-level progression defined in Slide 29 of the course:

1 Concept Level (Slide 29)
ERD & Domain Classes

Entity classes identified from problem domain: User (with roles Student, Instructor, Advisor, Admin), Course, Session, AttendanceRecord, Excuse, CounselingNote, AuditLog.

2 Logic Level (Slide 29)
Relational Tables

Mapped to 8 relational tables with strictly defined Primary Keys (PK), Foreign Keys (FK), unique constraints, and check constraints per normalization rules.

3 Physic Level (Slide 29)
SQLite3 DBMS

Implemented in SQLite3 engine with PRAGMA foreign_keys = ON;, B-tree primary indices, and automated ACID rollback handling.

Relational Conversion Rules Applied from Course Chapter 3

Slides 31–42
Class to Table Mapping (Slide 31) Slide 31

• A class ➔ a Table (e.g. Class Course ➔ Table Courses)
• A property ➔ a column (e.g. course_name ➔ Column course_name)
• An object ➔ a row (tuple) in the relational table.

Inheritance: Single Table + Discriminator (Slides 41–42) Slides 41–42

In Slide 42, superclass NhanVien and subclasses NhanVienCongNhat, NhanVienBienChe are mapped to a single table with discriminator column Loai_NV. In SAS, superclass User and subclasses Student, Instructor, Advisor, Admin are mapped to table Users with discriminator column role.

1-n Relationship: Reference Key (Slides 35–36) Slides 35–36

In Slide 35, primary key MA of Table A becomes a reference key (foreign key) in Table B. In SAS, Courses.id becomes Sessions.course_id; Users.id becomes Attendance.student_id, Excuses.student_id, Counseling_Notes.student_id, and Audit_Logs.user_id.

n-n Relationship: Intermediate Table (Slides 37–38) Slides 37–38

In Slide 37, A (0..n) <-> (0..n) B is resolved by creating an intermediate table C(MA, MB). In SAS, Students and Courses have a many-to-many relationship, resolved by intermediate table Enrollments(user_id PK/FK, course_id PK/FK).
